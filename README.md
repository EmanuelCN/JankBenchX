# JankBenchX

JankBenchX measures Android UI rendering on the device. Choose workloads and repetitions on the **Benchmark** tab, then press **Run Benchmark**. All supported workloads start enabled. Use **Select all** or **Clear all** beside **Workloads** to change the selection together. Wide-gamut animation appears when Android reports that wide-gamut rendering is supported. Keep the benchmark in the foreground until it opens **Results**. **History** opens and deletes saved runs. **Compare runs** aligns frame metrics by workload and shows each run’s selection, repetition count, and observed refresh rate. Workload selection and repeat count are remembered. Results start with the overall score and frame performance. Open workload rows to see full timings and pass diagnostics, or open the percentile chart to compare workloads.

The catalog includes the original UI workloads from JankBenchX. It scrolls real ListViews through alternating fling-shaped passes, edits an actual text field, blends ten overlapping full-size layers, and repeatedly changes and draws a bitmap. The two text lists use their intended 80% and 20% reusable word mixes. The image list continues to decode its images in the background as rows bind.

Other workloads model interactions common in modern apps. Photo Gallery Fling uses the native RecyclerView fling in a four-column grid of preloaded photo thumbnails and measures scrolling in both directions. The RecyclerView and Compose image feeds use the same bundled photos, row geometry, dataset, and timed scroll path. The nested feed scrolls vertically through horizontal photo carousels with asynchronous decoding. The detail transition moves between a feed and its photo detail view, recording time from initiating the transition to the first detail draw on the UI thread. Transition images are downsampled to a bounded pixel size. Live feed updates insert, remove, and change visible rows during a scroll.

The catalog also adapts 27 scenarios from the [public Android 17 AOSP UiBench app](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android17-release/tests/UiBench/AndroidManifest.xml), counting the two activities in its transition as one scenario and omitting its menu. Where UiBench and earlier entries use the same workload driver, the newer UiBench entry appears once. This includes text, overdraw, bitmap upload, nested lists, and the feed-to-detail transition. Other scenarios cover list clipping and inflation, expensive binding, view invalidation, hardware layer resizing, OpenGL texture compositing, offline WebView scrolling, and drawers. TV Browse Grid remains in saved results under its original name. The shade is an in-app notification stack, and window insets use a controlled editor relayout fixture. These adaptations measure app-window frames. Wide-gamut animation requires a compatible display.

## Measurements and scoring

On Android 15 and later, the app opts its windows out of adaptive refresh-rate power savings where the device supports that setting. Android chooses the display mode using the device's refresh-rate policy and user settings. Results show the highest observed rate. Compare runs with similar observed refresh rates.

- The runner uses app-owned UI actions on the main thread. One timing thread serves all passes in a run. Each pass draws a short warm-up before timing begins and uses the final workload frame or a post-workload report to confirm the capture ended. The progress wave keeps moving at the current pass position throughout the run. Timestamp filtering excludes launch, warm-up, and handoff frames. Incomplete timing captures get one fresh attempt. A valid capture is scored regardless of jank, and a pass with two incomplete captures or a workload error is marked failed.
- Average and percentile frame times use measured total durations in milliseconds. P50, P90, P95, and P99 use linear interpolation over sorted samples. Jank counts frames whose total duration reaches or exceeds the system-provided FrameMetrics deadline. When a deadline is unavailable, the display refresh period supplies the budget. Run comparisons show the range observed by the collector. The deadline graph shows the budget used for each frame.
- The P95 chart uses the same 0–33.3 ms axis in every run and labels measured values above the chart limit. P95 and P99 deadline overrun are computed from each frame's total duration minus its budget. Negative values indicate time remaining.
- On API 36 and later, compositor diagnostics match available SurfaceFlinger reports to captured frames by vsync ID. Coverage is reported alongside app, compositor, and other-system counts. Those causes can overlap. The diagnostic does not alter the score.
- Version 3 retains the original score's mean × jank percentage × sample deviation structure. Frames at or above 75% of their budget contribute to the mean and sample deviation. Their durations are expressed in 60 Hz equivalent milliseconds by multiplying each duration-to-budget ratio by 1000/60. The pass score is 1 + mean × jank percentage × max(1, sample deviation). The positive baseline represents a run without missed deadlines, and the deviation floor ensures consistently slow frames still carry a penalty. Lower scores are better. A small number of very long stalls can raise both the mean and deviation considerably. Pass details show the inputs to the score, including the budget-normalized mean and deviation. Four-digit measurements are rounded for display.
- A workload score is the geometric mean of its pass scores. The overall score is the geometric mean of the selected workloads. Every selected pass needs a valid capture for an overall score. Compare runs with the same selection and repetition count. Changes to the input driver, the corrected text mix, and the frame budgeting and scoring rules make version 3 results incomparable with older versions.
- The app writes run metadata and measurements to private SQLite storage. An interrupted run keeps any completed passes and is saved as cancelled. Schema upgrades preserve the version 1 and 2 frame tables. History shows runs recorded with scoring version 3, which have the required run status, workload selection, and device metadata. Older saved runs keep their measurements and scores. Shared workload drivers use the current workload name in both results and comparisons.

## Build

Use JDK 17 and the Android SDK Platform 37.0 and Build Tools 37.0.0. Set `JAVA_HOME` and `ANDROID_HOME`, or point `sdk.dir` in `local.properties` to the SDK.

```sh
./gradlew :app:assembleDebug :app:testDebugUnitTest :app:lintDebug
```
